# Аккаунт таргетолога и лиды из Google-таблицы — дизайн

**Дата:** 2026-10-03 · **Статус:** на согласовании у пользователя · **Ветка:** `feat/marketer-leads`

## Цель

Внешний таргетолог получает в CRM свой аккаунт. Лиды из его Google-таблицы попадают в CRM: сотрудники клиники видят их в разделе «Лиды», звонят и записывают на приём, а таргетолог видит только свои лиды и что с каждым стало.

## Решения пользователя

| Вопрос | Решение |
|---|---|
| Что видит таргетолог | Только лиды из своей таблицы и статус каждого: новый, в работе, не дозвонились, записан, пришёл, отказ, некачественный. Пациентов, записи, кассу, отчёты и ИИ-ассистента не видит. |
| Как подключается таблица | CRM сама читает таблицу: таргетолог даёт доступ «Читатель» служебному адресу Google, CRM забирает новые строки каждые 5 минут. |
| Как лиды попадают в таблицу | Неизвестно. Колонки не угадываются по позиции: соответствие «колонка → телефон / имя» выбирает человек при подключении. |
| Кто работает с лидами | Оператор колл-центра, ресепшен, менеджер; владелец (superadmin) видит всё. Директор, врач, медсестра, кассир и бухгалтер раздела не видят. |

Принято по умолчанию (меняется одной строкой, если владелец решит иначе):

- Роль в коде `marketer`, в интерфейсе «Таргетолог» / «Targetolog».
- Таргетолог видит по своему лиду: дату, имя, телефон, название источника, статус. Не видит: заметки сотрудников, кто из сотрудников работал с лидом, остальные колонки таблицы, данные пациента и записи.
- Источники, привязку аккаунта таргетолога и импорт настраивает только superadmin.
- Одна заявка на один телефон в рамках источника. Если в таблице есть надёжная колонка с номером заявки, источник можно завести в режиме «по номеру заявки».
- История изменений лида не ведётся: хранится текущий статус, одна заметка, кто и когда менял последним.

Отклонены:

- **Скрипт в таблице таргетолога, который сам отправляет строки.** Триггеры Apps Script не срабатывают на строки, записанные через API (так пишут рекламные коннекторы), поэтому скрипту всё равно пришлось бы опрашивать таблицу по таймеру. Ключ CRM лежал бы в чужой таблице и был бы виден всем её редакторам. Понадобился бы открытый адрес для приёма личных данных без входа в систему.
- **Публикация таблицы как CSV.** Имена и телефоны были бы доступны любому по ссылке.
- **Лиды как пациенты-заглушки или как задачи колл-центра.** Все таблицы колл-центра требуют `patient_id`; заглушки засорили бы базу пациентов, обзвон и отчёты.

## Этапы

Каждый этап выкладывается отдельно и полезен сам по себе.

| № | Что появляется | Зависит от |
|---|---|---|
| 1 | Аккаунт таргетолога и защита системы от внешнего аккаунта | — |
| 2 | Раздел «Лиды» для сотрудников; лиды добавляются вставкой строк из таблицы | 1 (только для привязки аккаунта) |
| 3 | Страница «Мои лиды» для таргетолога | 1, 2 |
| 4 | Лид → пациент → запись; «Записан» и «Пришёл» выставляются сами | 2 |
| 5 | Автоматическое чтение Google-таблицы | 2, служебный аккаунт Google, образец таблицы |

Этапы 4 и 5 друг от друга не зависят. Этап 5 начинается, когда готовы служебный аккаунт Google и образец таблицы таргетолога.

## Этап 1. Аккаунт таргетолога

### Роль

- `marketer` добавляется в `USER_ROLES` в `services/api/src/auth/permissions.ts` и в зеркальный `apps/web/src/auth/permissions.ts`.
- Строка прав роли — `{}`, написана с нуля и остаётся пустой на всех этапах. Копировать строку другой роли нельзя: у каждой существующей роли есть ИИ-ассистент и чтение пациентов и записей.
- Новый список `EXTERNAL_ROLES = ["marketer"]` в обоих приложениях.
- `marketer` добавляется в `APPOINTMENT_CLINICAL_HIDDEN_ROLES` (`clinicalDataScope.ts`): если роли когда-нибудь по ошибке дадут чтение записей, клинические поля останутся скрыты.
- Superadmin создаёт аккаунт на существующей странице «Пользователи»: роль появляется в списке сама, привязка к врачу не нужна.

Правило для владельца: таргетологу создаётся новый аккаунт. Переводить в эту роль аккаунт сотрудника нельзя: его прежний токен живёт до 8 часов.

### Миграция `037_users_role_marketer.sql`

```sql
SET LOCAL lock_timeout = '5s';
ALTER TABLE users DROP CONSTRAINT IF EXISTS users_role_check;
```

В production ограничения на роль нет (проверено запросом к каталогу 03.10.2026), там это пустая операция. В базе, собранной из файлов миграций, ограничение из `002_users.sql` не пустило бы новую роль. Ограничение не возвращается: значения ролей в production не проверены, а проверка отклоняла бы любое обновление строки с устаревшей ролью, включая обновление при входе. Список ролей проверяет API.

### Веб

- `CLINIC_STAFF` = все роли, кроме внешних. Сейчас это все роли, и новая роль получила бы «Панель управления» и ИИ-ассистента.
- После входа таргетолог видит статичную страницу «Кабинет таргетолога» без запросов данных. Она отрисовывается прямо в `RoleAwareHomeRedirect` на `/dashboard`: все перенаправления приложения сходятся на `/dashboard`, поэтому переход на ещё не существующий маршрут зациклился бы.
- Нижняя панель на телефоне (`MobileBottomNav`) для внешних ролей не показывается: её четыре вкладки не учитывают роль.
- Названия ролей на странице «Пользователи» и в шапке показываются переводом, а не идентификатором. Один общий словарь `ROLE_LABEL_KEYS`; ключи — литералы, иначе `check-i18n` их не проверит.
- Строки в `ru.json` и `uz.json`.

### Тесты

- Матрица: `marketer` получает отказ на каждом модуле и действии и не входит ни в один именованный список прав (оба приложения).
- Обход настоящего роутера API с токеном таргетолога: 403 везде, кроме явного списка разрешённых адресов (`/auth/me`, `/auth/logout`, `/auth/change-password`, `/clinic/me`, `/meta/clinic`, `/platform/access`).
- `POST /api/clinics`: 403 для таргетолога и для superadmin клиники, 201 для администратора платформы.
- Пользователь, созданный superadmin клиники 2, оказывается в клинике 2; тело с клиникой 1 — 403.
- `requireAuth`: токен сотрудника не вызывает запроса к базе; токен таргетолога после отключения, удаления или смены роли даёт 401; ошибка базы не пропускает запрос.
- `GET /api/clinic/me` для таргетолога — без полей подписки, для ресепшен — с ними.
- Миграция 037 на трёх видах базы: с ограничением из 002, без ограничения, с устаревшим списком ролей; повторный запуск без ошибок.
- Веб: таргетолог получает свою страницу без запросов к API, не панель управления; меню и нижняя панель пусты; у остальных ролей всё как раньше.

Порядок выкладки: сначала API (Render), затем веб (Vercel).

## Этап 2. Раздел «Лиды» для сотрудников

### Таблицы — миграция `038_leads.sql`

```sql
SET LOCAL lock_timeout = '5s';

CREATE TABLE IF NOT EXISTS lead_sources (
  id BIGSERIAL PRIMARY KEY,
  clinic_id BIGINT NOT NULL REFERENCES clinics(id),
  name TEXT NOT NULL CHECK (char_length(btrim(name)) BETWEEN 1 AND 100),
  marketer_user_id BIGINT NULL REFERENCES users(id),
  key_mode TEXT NOT NULL DEFAULT 'phone' CHECK (key_mode IN ('phone', 'external_id')),
  created_by BIGINT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT lead_sources_clinic_id_id_key UNIQUE (clinic_id, id)
);

CREATE TABLE IF NOT EXISTS leads (
  id BIGSERIAL PRIMARY KEY,
  clinic_id BIGINT NOT NULL,
  source_id BIGINT NOT NULL,
  external_key TEXT NOT NULL CHECK (char_length(external_key) BETWEEN 3 AND 200),
  full_name TEXT NULL CHECK (full_name IS NULL OR char_length(full_name) BETWEEN 1 AND 200),
  phone TEXT NOT NULL CHECK (phone ~ '^[0-9]{10,15}$'),
  extra JSONB NOT NULL DEFAULT '{}'::jsonb
    CHECK (jsonb_typeof(extra) = 'object' AND octet_length(extra::text) <= 8000),
  status TEXT NOT NULL DEFAULT 'new'
    CHECK (status IN ('new', 'in_progress', 'no_answer', 'booked', 'declined', 'invalid')),
  note TEXT NULL CHECK (note IS NULL OR char_length(note) <= 2000),
  patient_id BIGINT NULL REFERENCES patients(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  staff_updated_at TIMESTAMPTZ NULL,
  staff_updated_by BIGINT NULL REFERENCES users(id),
  CONSTRAINT leads_source_fkey
    FOREIGN KEY (clinic_id, source_id) REFERENCES lead_sources (clinic_id, id),
  CONSTRAINT leads_clinic_source_key UNIQUE (clinic_id, source_id, external_key)
);

CREATE INDEX IF NOT EXISTS idx_leads_clinic_recent ON leads (clinic_id, id DESC);
```

- **Источник** (`lead_sources`) — одна таблица одного таргетолога. `marketer_user_id` — единственное, что определяет, чьи лиды видит таргетолог; `NULL` — никто вне клиники источник не видит.
- Только добавления: ни одна существующая строка не затрагивается, оператор не может упасть на существующих данных.
- Все уникальные ключи начинаются с `clinic_id`. Лид привязан к источнику своей клиники составным внешним ключом.
- Поля лида делятся на два набора, которые не пересекаются. Импорт один раз пишет `external_key`, `full_name`, `phone`, `extra` и больше их не меняет. Сотрудники пишут `status`, `note`, `patient_id`, `staff_updated_*`. Повторный импорт не может стереть работу сотрудников.

### Статусы

| Статус | В интерфейсе | Когда |
|---|---|---|
| `new` | Новый | Пришёл из таблицы, никто не трогал. Ставит только импорт. |
| `in_progress` | В работе | Сотрудник нажал «Взять в работу». |
| `no_answer` | Не дозвонились | Позвонили, не ответил. |
| `booked` | Записан | Ставится вручную; с этапа 4 показывается сам, когда у привязанного пациента есть запись. |
| `declined` | Отказ | Дозвонились, не интересно. |
| `invalid` | Некачественный | Неверный номер, спам, тест, не целевой. |
| `visited` | Пришёл | Не хранится, вычисляется на этапе 4. |

### Права

| Роль | Модуль `leads` |
|---|---|
| superadmin | всё |
| reception, operator, manager | read, update |
| director, doctor, nurse, cashier, accountant | нет |
| marketer | нет (строка прав пустая) |

Именованный ключ `LEAD_SOURCES_MANAGE = ["superadmin"]`: источники, привязка таргетолога, импорт. Создавать и удалять лиды вручную нельзя: таких адресов нет.

### API

Маршруты подключаются в `routes/index.ts` за `requireAuth` и проверкой подписки. Порядок файлов — как у электронной очереди: типы и интерфейс, `PostgresLeadsRepository` с явным `clinicId` в каждом методе, `leadsService`, `container/services.ts`, контроллер, валидаторы, `routes/leadsRoutes.ts`.

| Адрес | Доступ | Назначение |
|---|---|---|
| `GET /api/leads` | `leads.read` | Список клиники, новые сверху. Фильтры: статус, источник; постранично по `id`. |
| `PATCH /api/leads/:id` | `leads.update` | `{status?, expectedStatus?, note?}`. Если коллега успел изменить статус — 409. В `new` вернуть нельзя. |
| `GET /api/leads/sources` | `leads.read` | Источники для фильтра; для superadmin — с привязкой и настройками. |
| `POST /api/leads/sources` | `LEAD_SOURCES_MANAGE` | Создать источник. |
| `PATCH /api/leads/sources/:id` | `LEAD_SOURCES_MANAGE` | Переименовать, привязать или отвязать таргетолога. Режим ключа после первого импорта не меняется. |
| `POST /api/leads/sources/:id/import` | `LEAD_SOURCES_MANAGE` | Импорт вставкой: до 500 строк за запрос. Ответ: сколько добавлено, сколько уже было, какие строки пропущены и почему (номера строк и коды причин, без значений ячеек). |

Привязка таргетолога проверяется в SQL при сохранении источника: пользователь той же клиники, роль `marketer`, активен, не удалён; иначе 422.

### Приём строк

Одна функция `ingestLeadRows(clinicId, sourceId, rows)` — единственное место, где создаются лиды. Её вызывают импорт вставкой (этап 2) и чтение таблицы (этап 5). Строки приходят типизированными: `{phone, fullName?, externalId?, extra?}`. Сопоставление колонок с полями — дело вызывающего.

**Телефон** приводится к виду «только цифры» новой функцией `services/api/src/utils/phone.ts`:

1. Число из таблицы должно быть безопасным целым; иначе строка пропускается.
2. Из текста убираются пробелы по краям, неразрывный пробел, ведущий апостроф и короткая метка вида `p:`.
3. Если после этого есть что-то, кроме цифр, одного ведущего `+`, пробелов, скобок, точек и дефисов, строка пропускается. Так отсекается запись вида `9.98E+11`.
4. 12 цифр, начинающихся с `998`, с допустимым кодом оператора — оставить. 9 цифр с допустимым кодом — дописать `998`. Любые другие 10–15 цифр — оставить как иностранный номер. Иначе строка пропускается.

Строка без пригодного телефона не сохраняется, а считается в ответе: сотруднику нечего делать с лидом, которому нельзя позвонить. `+998 90 123-45-67` текстом и `998901234567` числом дают одно значение.

**Ключ строки** `external_key`, уникален в паре с клиникой и источником:

- режим `phone` (по умолчанию): `p:` + телефон;
- режим `external_id`: `id:` + номер заявки из таблицы (текст 1–100 символов; число длиннее 15 цифр отклоняется, потому что таблица могла его округлить).

Номер строки таблицы и дата в ключ не входят: строки сортируют и удаляют, а дата приходит текстом при вставке и числом через API.

**Запись** — один оператор на пачку:

```sql
INSERT INTO leads (clinic_id, source_id, external_key, full_name, phone, extra)
SELECT s.clinic_id, s.id, r.external_key, r.full_name, r.phone, r.extra
FROM lead_sources s
CROSS JOIN jsonb_to_recordset($3::jsonb)
  AS r(external_key text, full_name text, phone text, extra jsonb)
WHERE s.id = $1 AND s.clinic_id = $2
ON CONFLICT (clinic_id, source_id, external_key) DO NOTHING
RETURNING id
```

Клиника лида копируется из строки источника внутри SQL. Источник чужой клиники не совпадает ни с одной строкой, ничего не вставляется. `ON CONFLICT` обязателен: общий обработчик ошибок возвращает текст PostgreSQL со значениями ключа.

**Повторный импорт** только добавляет. Уже известный ключ пропускается, поэтому повторная вставка всей таблицы добавляет 0 строк. Правка или удаление строки в таблице в CRM ничего не меняет: таргетолог не может ни переписать, ни стереть запись клиники.

В логи пишутся номер источника, количества и коды; значения ячеек не пишутся.

### Веб

- Страница «Лиды» (`/leads`, `apps/web/src/modules/leads`): таблица — когда пришёл, имя, телефон ссылкой для звонка, источник, статус, кто менял последним. Фильтры по статусу и источнику. «Взять в работу» на новом лиде. В раскрытой строке — остальные колонки таблицы, выбор статуса, заметка. Кнопки «Обновить» и «Показать ещё».
- Блок «Источники и импорт» на той же странице, только для superadmin (как блок ТВ-экранов на странице очереди). Импорт: выбрать источник, вставить скопированные из таблицы строки вместе с заголовком, подтвердить предложенные колонки (телефон, имя, номер заявки, дополнительные), увидеть первые 5 строк, получить итог «Добавлено N, уже были M, пропущено K».
- Пункт меню «Лиды» для ролей с `leads.read`.

Ручная вставка остаётся и после этапа 5 как запасной способ: если таблица перестала читаться, лиды всё равно можно внести за минуту.

## Этап 3. «Мои лиды» для таргетолога

- Именованный ключ `LEADS_OWN_READ = ["marketer"]` и один адрес `GET /api/leads/mine`. Это единственный адрес с данными, доступный таргетологу.
- Адрес не принимает ни источник, ни клинику. Запрос:

```sql
SELECT l.created_at, l.full_name, l.phone, s.name AS source_name, l.status
FROM leads l
JOIN lead_sources s ON s.clinic_id = l.clinic_id AND s.id = l.source_id
WHERE l.clinic_id = $1 AND s.marketer_user_id = $2 [AND l.id < $3]
ORDER BY l.id DESC LIMIT $4
```

  `$1` и `$2` берутся из токена. С этапа 4 вместо `l.status` подставляется вычисленный статус. Не выбираются: `extra`, `note`, `patient_id`, имена и номера сотрудников, время работы с лидом.
- Остальные адреса лидов закрыты `checkPermission('leads', …)`, который пустая строка прав пройти не может, включая адреса, которые добавят позже.
- Страница «Мои лиды» (`/my-leads`), отдельный файл сборки: таблица только для чтения — дата, имя, телефон, источник, статус; «Показать ещё». После входа таргетолог попадает сюда; статичная страница этапа 1 убирается.
- При блокировке подписки клиники внешняя роль видит нейтральное «Доступ временно недоступен» без контактов продавца CRM.

Тесты: таргетолог А не видит источник таргетолога Б в той же клинике и ничего из клиники 2; после отвязки источника список пуст с тем же токеном; набор полей ответа равен разрешённому списку; отключённый аккаунт получает 401.

## Этап 4. Лид → пациент → запись

Миграция не нужна (`patient_id` уже есть), API записей и пациентов не меняется.

- Лид никогда не становится пациентом сам. Связь — только `leads.patient_id`, её ставит сотрудник. Автоматической привязки по телефону нет: одним номером пользуются семьи, и в `patients` телефон не уникален.
- `GET /api/leads/:id/patient-matches` — до 5 пациентов клиники, у которых последние 9 цифр телефона совпадают с лидом. Только подсказка. Индекс на `patients` не добавляется: построение индекса в стартовой миграции рискованнее, чем просмотр пациентов одной клиники по нажатию.
- `PUT /api/leads/:id/patient` `{patientId | null}` — привязать или отвязать. Проверка клиники пациента внутри того же `UPDATE`; чужой пациент — 404.
- «Создать пациента» — существующий `POST /api/patients` с именем и телефоном из лида (их можно поправить) и источником `advertising`, затем привязка.
- «Записать на приём» — существующая ссылка `/appointments?patientId=N`.
- «Записан» и «Пришёл» вычисляются при чтении по записям привязанного пациента, созданным после лида: есть запись в `scheduled`/`confirmed` — «Записан»; в `arrived`/`in_consultation`/`completed` — «Пришёл». Отменённая запись возвращает сохранённый статус. Тот же расчёт используется в `/api/leads/mine`; колонки пациента и записи таргетологу не отдаются.

Перед выкладкой проверить: `AppointmentsPage` молча отбрасывает `patientId`, если пациента нет в загруженном списке (`AppointmentsPage.tsx:525-531`); проверить с пациентом, созданным секунду назад.

## Этап 5. Автоматическое чтение Google-таблицы

### Миграция `039_lead_sources_sheet_sync.sql`

Новые колонки `lead_sources`: `spreadsheet_id`, `sheet_title`, `first_row` (с какой строки читать, по умолчанию 2), `column_map` (JSON), `verify_code`, `sync_enabled` (по умолчанию `FALSE`), `last_sync_at`, `last_sync_status` (короткий код). Проверка: синхронизацию нельзя включить без ссылки, листа, сопоставления колонок и кода.

### Как работает

- **Доступ.** Один служебный аккаунт Google на всю CRM, только чтение (`spreadsheets.readonly`). Ключ — одна переменная окружения Render, проверяется в `config/env.ts` как необязательная функция. Подпись запроса токена — `node:crypto`, запросы — `fetch` (на Render Node 22). Новых зависимостей нет.
- **Чтение.** Раз в 5 минут для каждого источника с включённой синхронизацией: лист целиком, `valueRenderOption=UNFORMATTED_VALUE`, лимит 20 секунд. Планировщик — по образцу напоминаний SMS (`smsReminderService.ts:107-126`), запускается в `server.ts`. Источники обрабатываются по очереди; ответ 429 останавливает цикл до следующего запуска.
- **Код проверки.** Таргетолог вписывает код источника в свободную ячейку строки заголовков. Без кода строки данных не читаются. Так служебный аккаунт нельзя направить на чужую таблицу, вписав её адрес.
- **Колонки.** Сопоставление хранится по тексту заголовка. Если заголовок пропал, цикл останавливается со статусом `columns_changed` и ничего не импортирует: переставленные колонки не должны положить телефоны в поле имени.
- **Ошибки.** Классифицируются по коду HTTP и полю `error.status`, не по тексту. Ошибка никогда не читается как «таблица пуста». В `last_sync_status` пишется короткий код.
- **Два экземпляра API или наложение запусков** только повторяют работу: вставка идемпотентна.

Квоты Google: 60 чтений в минуту на служебный аккаунт; одно чтение на источник раз в 5 минут далеко от предела.

### Веб

В форме источника: ссылка на таблицу и название листа; адрес служебного аккаунта, которому надо дать доступ «Читатель»; код проверки; с какой строки читать; «Проверить» (показывает заголовки и найден ли код); сопоставление колонок; переключатель синхронизации (доступен после успешной проверки); время и итог последнего чтения; «Синхронизировать сейчас».

### Что нужно до начала этапа

| Кто | Что |
|---|---|
| Владелец | Один раз создать проект в Google Cloud, включить Google Sheets API, создать служебный аккаунт без ролей и один ключ JSON, добавить ключ в переменные окружения Render. Бесплатно. |
| Таргетолог | Прислать строку заголовков и 2–3 строки-образца своей таблицы (данные можно заменить выдуманными). |
| Владелец и таргетолог | Одна проверка: таргетолог даёт служебному адресу доступ «Читатель» к таблице. Официальная документация Google не подтверждает этот случай для личного Gmail прямо, хотя на практике так делают. |

Если доступ дать не получится, этап 5 заменяется скриптом в таблице; этапы 1–4 от этого не зависят, ручная вставка продолжает работать.

## Что не делаем

- Таблицы истории и попыток звонков, закрепление лида за сотрудником с блокировкой, напоминания о перезвоне.
- Воронка, отчёты по конверсии, счётчики в меню, уведомления о новом лиде, выгрузка в CSV, стоимость лида.
- Добавление лида вручную по одному.
- Обновление лида при правке строки в таблице, удаление лидов при удалении строк, запись статусов обратно в таблицу.
- Новые значения `patients.source`, поля UTM, автоматическое создание пациентов.
- Индексы на `patients`, уникальный индекс на `users.username`, ограничение на `users.role`.
- Проверка токена по базе для сотрудников, сокращение срока жизни токена.

## Известные ограничения

- Срок хранения лидов, не ставших пациентами, не ограничен.
- В режиме «по телефону» повторная заявка с того же номера через полгода новым лидом не станет.
- Правка телефона в таблице в режиме «по телефону» создаёт второй лид; первый остаётся.
- Дата лида — когда его получила CRM. Дата из таблицы видна сотрудникам только текстом среди дополнительных колонок. Первый большой импорт покажет старые лиды как полученные сегодня.
- «Записан» и «Пришёл» на этапе 4 считают любую запись привязанного пациента, созданную после лида, в том числе не связанную с рекламой.
- Сотрудники после отключения аккаунта сохраняют доступ до 8 часов (как сейчас); мгновенное отключение работает только для внешних ролей.
- Журнал входов виден superadmin всех клиник без фильтра по клинике (существующая проблема, здесь не исправляется).
- Таблицы `clinics` и колонки `clinic_id` не создаются ни одной миграцией в репозитории: новые внешние ключи опираются на схему production, тесты используют заглушки таблиц и настоящий файл миграции.
- Утёкший ключ служебного аккаунта читает все таблицы, к которым этому аккаунту дали доступ, пока ключ не удалён.
