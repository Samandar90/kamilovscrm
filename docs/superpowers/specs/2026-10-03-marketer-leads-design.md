# Аккаунт таргетолога и лиды из Google-таблицы — дизайн

**Дата:** 2026-10-03 · **Статус:** утверждён пользователем («всё сделай сам») · **Ветка:** `feat/marketer-leads`

## Цель

Внешний таргетолог получает в CRM свой аккаунт. Лиды из его Google-таблицы сами попадают в CRM: сотрудники клиники видят их в разделе «Лиды», звонят и записывают на приём, а таргетолог видит только свои лиды и что с каждым стало.

## Решения пользователя

| Вопрос | Решение |
|---|---|
| Что видит таргетолог | Только лиды из своей таблицы и статус каждого: новый, в работе, не дозвонились, записан, пришёл, отказ, некачественный. Пациентов, записи, кассу, отчёты и ИИ-ассистента не видит. |
| Как подключается таблица | CRM сама читает таблицу. Пользователь прислал таблицу, открытую по ссылке, и попросил всё сделать без его участия, поэтому CRM читает её по ссылке, без служебного аккаунта Google. |
| Как лиды попадают в таблицу | Неизвестно, таблица пока пустая (один лист, заголовков нет). Колонки находятся по названию заголовка, а не по позиции; при нераспознанных заголовках их выбирает superadmin. |
| Кто работает с лидами | Оператор колл-центра, ресепшен, менеджер; владелец (superadmin) видит всё. Директор, врач, медсестра, кассир и бухгалтер раздела не видят. |

Принято по умолчанию:

- Роль в коде `marketer`, в интерфейсе «Таргетолог» / «Targetolog».
- Таргетолог видит по своему лиду: дату, имя, телефон, название источника, статус. Не видит: заметки сотрудников, кто работал с лидом, остальные колонки таблицы, данные пациента и записи.
- Источники, привязку аккаунта таргетолога и подключение таблицы настраивает только superadmin.
- Одна заявка на один телефон в рамках источника.
- История изменений лида не ведётся: хранится текущий статус, одна заметка, кто и когда менял последним.

Отклонены:

- **Служебный аккаунт Google.** Требует от владельца создать проект в Google Cloud и ключ. Остаётся запасным путём, если таблицу закроют по ссылке: добавляется второй способ чтения, таблицы и экраны не меняются.
- **Скрипт в таблице таргетолога, который сам отправляет строки.** Триггеры Apps Script не срабатывают на строки, записанные через API (так пишут рекламные коннекторы); ключ CRM лежал бы в чужой таблице; понадобился бы открытый адрес для приёма личных данных без входа в систему.
- **Ручная вставка строк.** Нужна была как первый способ, пока нет доступа Google; чтение по ссылке настройки не требует.
- **Лиды как пациенты-заглушки или как задачи колл-центра.** Все таблицы колл-центра требуют `patient_id`; заглушки засорили бы базу пациентов, обзвон и отчёты.

## Цена чтения по ссылке

Таблицу может прочитать любой, у кого есть ссылка на неё. Так её настроил владелец таблицы; CRM эту открытость не увеличивает, но зависит от неё: если доступ по ссылке закрыть, чтение остановится со статусом «нет доступа», лиды в CRM останутся. Идентификатор таблицы хранится в базе, виден только superadmin и не пишется в логи.

## Роль и защита

### Роль

- `marketer` добавляется в `USER_ROLES` в `services/api/src/auth/permissions.ts` и в зеркальный `apps/web/src/auth/permissions.ts`.
- Строка прав роли — `{}`, написана с нуля и остаётся пустой. Копировать строку другой роли нельзя: у каждой существующей роли есть ИИ-ассистент и чтение пациентов и записей.
- Новый список `EXTERNAL_ROLES = ["marketer"]` в обоих приложениях.
- `marketer` добавляется в `APPOINTMENT_CLINICAL_HIDDEN_ROLES` (`clinicalDataScope.ts`): если роли по ошибке дадут чтение записей, клинические поля останутся скрыты.
- Superadmin создаёт аккаунт на существующей странице «Пользователи».

### Веб

- `CLINIC_STAFF` = все роли, кроме внешних. Сейчас это все роли, и новая роль получила бы «Панель управления» и ИИ-ассистента.
- После входа таргетолог попадает на `/my-leads`: `RoleAwareHomeRedirect` перенаправляет внешнюю роль туда; маршрут открыт только этой роли, поэтому цикла перенаправлений нет.
- Нижняя панель на телефоне (`MobileBottomNav`) для внешних ролей не показывается.
- Названия ролей на странице «Пользователи» и в шапке показываются переводом. Один общий словарь `ROLE_LABEL_KEYS`; ключи — литералы, иначе `check-i18n` их не проверит.
- При блокировке подписки внешняя роль видит нейтральное «Доступ временно недоступен» без контактов продавца CRM.

## Данные — миграция `038_leads.sql`

```sql
SET LOCAL lock_timeout = '5s';

CREATE TABLE IF NOT EXISTS lead_sources (
  id BIGSERIAL PRIMARY KEY,
  clinic_id BIGINT NOT NULL REFERENCES clinics(id),
  name TEXT NOT NULL CHECK (char_length(btrim(name)) BETWEEN 1 AND 100),
  marketer_user_id BIGINT NULL REFERENCES users(id),
  spreadsheet_id TEXT NULL CHECK (spreadsheet_id IS NULL OR spreadsheet_id ~ '^[A-Za-z0-9_-]{20,100}$'),
  sheet_gid BIGINT NOT NULL DEFAULT 0 CHECK (sheet_gid >= 0),
  column_map JSONB NULL CHECK (column_map IS NULL OR jsonb_typeof(column_map) = 'object'),
  sync_enabled BOOLEAN NOT NULL DEFAULT FALSE,
  last_sync_at TIMESTAMPTZ NULL,
  last_sync_status TEXT NULL CHECK (last_sync_status IS NULL OR last_sync_status ~ '^[a-z0-9_]{1,40}$'),
  last_sync_rows INTEGER NULL,
  last_sync_skipped INTEGER NULL,
  created_by BIGINT NULL REFERENCES users(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  updated_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  CONSTRAINT lead_sources_clinic_id_id_key UNIQUE (clinic_id, id),
  CONSTRAINT lead_sources_sync_needs_sheet CHECK (NOT sync_enabled OR spreadsheet_id IS NOT NULL)
);

CREATE TABLE IF NOT EXISTS leads (
  id BIGSERIAL PRIMARY KEY,
  clinic_id BIGINT NOT NULL,
  source_id BIGINT NOT NULL,
  external_key TEXT NOT NULL CHECK (char_length(external_key) BETWEEN 3 AND 200),
  full_name TEXT NULL CHECK (full_name IS NULL OR char_length(full_name) BETWEEN 1 AND 200),
  phone TEXT NOT NULL CHECK (phone ~ '^[0-9]{10,15}$'),
  extra JSONB NOT NULL DEFAULT '{}'::jsonb CHECK (jsonb_typeof(extra) = 'object'),
  status TEXT NOT NULL DEFAULT 'new'
    CHECK (status IN ('new', 'in_progress', 'no_answer', 'booked', 'declined', 'invalid')),
  note TEXT NULL CHECK (note IS NULL OR char_length(note) <= 2000),
  patient_id BIGINT NULL REFERENCES patients(id),
  created_at TIMESTAMPTZ NOT NULL DEFAULT now(),
  staff_updated_at TIMESTAMPTZ NULL,
  staff_updated_by BIGINT NULL REFERENCES users(id),
  CONSTRAINT leads_source_fkey
    FOREIGN KEY (clinic_id, source_id) REFERENCES lead_sources (clinic_id, id),
  CONSTRAINT leads_clinic_source_key UNIQUE (clinic_id, source_id, external_key)
);

CREATE INDEX IF NOT EXISTS idx_leads_clinic_recent ON leads (clinic_id, id DESC);
```

- **Источник** (`lead_sources`) — один лист одной таблицы одного таргетолога. `marketer_user_id` — единственное, что определяет, чьи лиды видит таргетолог; `NULL` — никто вне клиники источник не видит.
- Лист задаётся номером `gid` из ссылки: он не меняется при переименовании листа.
- `column_map` = `NULL` — колонки определяются по заголовкам автоматически; иначе `{"phone": "<заголовок>", "name": "<заголовок>" | null}`.
- Только добавления: ни одна существующая строка не затрагивается.
- Все уникальные ключи начинаются с `clinic_id`. Лид привязан к источнику своей клиники составным внешним ключом.
- Поля лида делятся на два набора. Чтение таблицы один раз пишет `external_key`, `full_name`, `phone`, `extra` и больше их не меняет. Сотрудники пишут `status`, `note`, `patient_id`, `staff_updated_*`. Повторное чтение не может стереть работу сотрудников.

## Статусы

| Статус | В интерфейсе | Когда |
|---|---|---|
| `new` | Новый | Пришёл из таблицы, никто не трогал. Ставит только чтение таблицы. |
| `in_progress` | В работе | Сотрудник нажал «Взять в работу» или привязал пациента. |
| `no_answer` | Не дозвонились | Позвонили, не ответил. |
| `booked` | Записан | Ставится вручную или показывается сам, когда у привязанного пациента есть запись. |
| `declined` | Отказ | Дозвонились, не интересно. |
| `invalid` | Некачественный | Неверный номер, спам, тест, не целевой. |
| `visited` | Пришёл | Не хранится, вычисляется по записям привязанного пациента. |

«Записан» и «Пришёл» вычисляются при чтении по записям привязанного пациента, созданным после лида: есть запись в `arrived`/`in_consultation`/`completed` — «Пришёл»; иначе в `scheduled`/`confirmed` — «Записан»; иначе сохранённый статус. Отменённая запись возвращает сохранённый статус. Вычисленное значение называется `stage`.

| Роль | Модуль `leads` |
|---|---|
| superadmin | всё |
| reception, operator, manager | read, update |
| director, doctor, nurse, cashier, accountant | нет |
| marketer | нет (строка прав пустая) |

Именованные ключи: `LEAD_SOURCES_MANAGE = ["superadmin"]` (источники, привязка, подключение таблицы), `LEADS_OWN_READ = ["marketer"]` (один адрес `/api/leads/mine`). Создавать и удалять лиды вручную нельзя: таких адресов нет.

## API

Маршруты `/api/leads` подключаются в `routes/index.ts` за `requireAuth` и проверкой подписки. Порядок файлов — как у электронной очереди.

| Адрес | Доступ | Назначение |
|---|---|---|
| `GET /api/leads` | `leads.read` | Список клиники, новые сверху. Фильтры: `stage`, `sourceId`; постранично по `beforeId`. |
| `PATCH /api/leads/:id` | `leads.update` | `{status?, expectedStatus?, note?}`. Коллега успел изменить статус — 409. В `new` вернуть нельзя. |
| `GET /api/leads/:id/patient-matches` | `leads.read` + `PATIENT_READ` | До 5 пациентов клиники с теми же последними 9 цифрами телефона. Только подсказка. |
| `PUT /api/leads/:id/patient` | `leads.update` + `PATIENT_READ` | `{patientId \| null}`. Привязать или отвязать. Чужой пациент — 404. |
| `GET /api/leads/sources` | `leads.read` | Источники для фильтра: `id`, `name`. |
| `GET /api/leads/sources/manage` | `LEAD_SOURCES_MANAGE` | Источники с привязкой, таблицей и состоянием чтения. |
| `POST /api/leads/sources` | `LEAD_SOURCES_MANAGE` | Создать источник. |
| `PATCH /api/leads/sources/:id` | `LEAD_SOURCES_MANAGE` | Имя, таргетолог, ссылка на таблицу, колонки, включение чтения. |
| `POST /api/leads/sources/:id/check` | `LEAD_SOURCES_MANAGE` | Прочитать таблицу без записи: заголовки, найденные колонки, сколько строк годится. |
| `POST /api/leads/sources/:id/sync` | `LEAD_SOURCES_MANAGE` | Прочитать таблицу сейчас. |
| `GET /api/leads/mine` | `LEADS_OWN_READ` | Единственный адрес с данными для таргетолога. |

Привязка таргетолога проверяется в SQL при сохранении источника: пользователь той же клиники, роль `marketer`, активен, не удалён; иначе 422.

### `GET /api/leads/mine`

Адрес не принимает ни источник, ни клинику:

```sql
SELECT l.id, l.created_at, l.full_name, l.phone, s.name AS source_name, <stage>
FROM leads l
JOIN lead_sources s ON s.clinic_id = l.clinic_id AND s.id = l.source_id
WHERE l.clinic_id = $1 AND s.marketer_user_id = $2 [AND l.id < $3]
ORDER BY l.id DESC LIMIT $4
```

`$1` и `$2` берутся из токена; `<stage>` — выражение из раздела «Статусы». Не выбираются: `extra`, `note`, `patient_id`, имена и номера сотрудников, время работы с лидом, колонки пациента и записи. Остальные адреса лидов закрыты `checkPermission('leads', …)` или `LEAD_SOURCES_MANAGE`, которые пустая строка прав пройти не может, включая адреса, которые добавят позже.

## Чтение таблицы

### Откуда

`https://docs.google.com/spreadsheets/d/<id>/export?format=csv&gid=<gid>`. Адрес строится сервером из проверенных `spreadsheet_id` и `sheet_gid`; произвольный адрес пользователь задать не может. Перенаправления обрабатываются вручную, не больше 5; допустимы только `docs.google.com` и `*.googleusercontent.com`. Перенаправление на любой другой узел (например, страницу входа Google) означает «нет доступа». Лимит 20 секунд и 5 МБ. Новых зависимостей нет: `fetch` из Node 22 и свой разбор CSV.

Superadmin вставляет в форму источника обычную ссылку на таблицу; сервер достаёт из неё `id` и `gid`.

### Колонки

- Строка заголовков — первая из первых 10 строк, где найден заголовок телефона.
- Заголовок сравнивается после приведения: нижний регистр, без пробелов, подчёркиваний, дефисов, точек и двоеточий.
- Телефон: `телефон`, `номертелефона`, `телефонныйномер`, `тел`, `моб`, `мобильный`, `мобильныйтелефон`, `номер`, `phone`, `phonenumber`, `mobile`, `mobilephone`, `tel`, `telefon`, `telefonraqami`, `telefonraqam`, `raqam`.
- Имя: `имя`, `фио`, `имяифамилия`, `клиент`, `имяклиента`, `полноеимя`, `name`, `fullname`, `firstname`, `ism`, `ismfamiliya`, `ismi`, `fio`, `mijoz`.
- Если задан `column_map`, используются его заголовки. Заголовок пропал — статус `columns_not_found`, ничего не импортируется: переставленные колонки не должны положить телефоны в поле имени.
- Остальные непустые колонки сохраняются в `extra` как `{заголовок: текст}`: не больше 40 колонок, значение до 500 символов. Видны только сотрудникам.

### Телефон

Приводится к виду «только цифры» функцией `services/api/src/utils/phone.ts`:

1. Число должно быть безопасным целым; иначе строка пропускается.
2. Из текста убираются пробелы по краям, неразрывный пробел, ведущий апостроф и короткая метка вида `p:`.
3. Если после этого есть что-то, кроме цифр, одного ведущего `+`, пробелов, скобок, точек и дефисов, строка пропускается. Так отсекается запись вида `9.98E+11`.
4. Ведущие `00` убираются. 12 цифр, начинающихся с `998`, с допустимым кодом оператора — оставить. 9 цифр с допустимым кодом — дописать `998`. Любые другие 10–15 цифр — оставить как иностранный номер. Иначе строка пропускается.

Допустимый национальный номер Узбекистана: `^(?:20|33|[5-9]\d)\d{7}$`. Строка без пригодного телефона не сохраняется, а считается: сотруднику нечего делать с лидом, которому нельзя позвонить. `+998 90 123-45-67` и `998901234567` дают одно значение.

### Запись

Ключ строки `external_key` = `p:` + телефон. Номер строки таблицы и дата в ключ не входят: строки сортируют и удаляют. Одна функция `ingestLeadRows(clinicId, sourceId, rows)` — единственное место, где создаются лиды:

```sql
INSERT INTO leads (clinic_id, source_id, external_key, full_name, phone, extra)
SELECT s.clinic_id, s.id, r.external_key, r.full_name, r.phone, r.extra
FROM lead_sources s
CROSS JOIN jsonb_to_recordset($3::jsonb)
  AS r(external_key text, full_name text, phone text, extra jsonb)
WHERE s.id = $1 AND s.clinic_id = $2
ON CONFLICT (clinic_id, source_id, external_key) DO NOTHING
RETURNING id
```

Клиника лида копируется из строки источника внутри SQL. `ON CONFLICT` обязателен: общий обработчик ошибок возвращает текст PostgreSQL со значениями ключа. Повторное чтение только добавляет: правка или удаление строки в таблице в CRM ничего не меняет, таргетолог не может ни переписать, ни стереть запись клиники.

### Расписание

- Планировщик в процессе API по образцу напоминаний SMS: первый запуск через 60 секунд после старта, затем каждые 5 минут. Выключается переменной `LEADS_SHEET_SYNC_ENABLED=false`; работает только с `DATA_PROVIDER=postgres`.
- Источники с включённым чтением обрабатываются по очереди. Клиника передаётся явно из строки источника: запроса и его контекста здесь нет.
- Если содержимое таблицы не изменилось с прошлого чтения (хеш в памяти процесса), строки не разбираются, обновляется только время.
- Не больше 5000 строк; запись пачками по 500.
- Два экземпляра API или наложение запусков только повторяют работу: вставка идемпотентна.

### Статусы чтения

| Код | Смысл |
|---|---|
| `ok` | Прочитано. |
| `empty` | В таблице пока нет строк. Не ошибка. |
| `no_access` | Таблица не открыта по ссылке. |
| `not_found` | Таблица или лист не найдены. |
| `columns_not_found` | Не найдена колонка телефона. |
| `too_large` | Больше 5 МБ или 5000 строк. |
| `timeout` | Google не ответил за 20 секунд. |
| `http_error` | Другая ошибка сети или ответа. |

Ошибка никогда не читается как «таблица пуста». В логи пишутся номер источника, количества и коды; значения ячеек и идентификатор таблицы не пишутся.

## Лид → пациент → запись

API записей и пациентов не меняется.

- Лид никогда не становится пациентом сам. Связь — только `leads.patient_id`, её ставит сотрудник. Автоматической привязки по телефону нет: одним номером пользуются семьи, и в `patients` телефон не уникален.
- Подсказка пациентов — по нажатию, для одного лида. Индекс на `patients` не добавляется.
- «Создать пациента» — существующий `POST /api/patients` с именем и телефоном из лида (их можно поправить) и источником `advertising`, затем привязка.
- «Записать на приём» — существующая ссылка `/appointments?patientId=N`.

## Веб

- **«Лиды»** (`/leads`, `apps/web/src/modules/leads`) для ролей с `leads.read`: таблица — когда пришёл, имя, телефон ссылкой для звонка, источник, статус. Фильтры по статусу и источнику. «Взять в работу» на новом лиде. В раскрытой строке — остальные колонки таблицы, выбор статуса, заметка, блок пациента (подсказки, «Привязать», «Создать пациента», «Записать на приём», «Отвязать»). «Обновить» и «Показать ещё».
- **«Источники»** — блок на той же странице, только для superadmin (как блок ТВ-экранов на странице очереди): имя, таргетолог, ссылка на таблицу, «Проверить», выбор колонок телефона и имени, переключатель чтения, время и итог последнего чтения, «Прочитать сейчас».
- **«Мои лиды»** (`/my-leads`) для таргетолога, отдельный файл сборки: таблица только для чтения — дата, имя, телефон, источник, статус; «Показать ещё».

## Тесты

- Матрица: `marketer` получает отказ на каждом модуле и действии и входит только в `LEADS_OWN_READ` (оба приложения).
- Обход настоящего роутера API с токеном таргетолога: 403 везде, кроме явного списка разрешённых адресов.
- `POST /api/clinics`: 403 для таргетолога и для superadmin клиники, 201 для администратора платформы.
- Пользователь, созданный superadmin клиники 2, оказывается в клинике 2.
- `requireAuth`: токен сотрудника не вызывает запроса к базе; токен таргетолога после отключения, удаления или смены роли даёт 401; ошибка базы не пропускает запрос.
- Миграции 037 и 038 на PGlite, повторный запуск без ошибок.
- Лиды на PGlite через настоящий роутер, со второй клиникой: повторное чтение добавляет 0; статус и заметка переживают повторное чтение; лид или источник чужой клиники — 404; таргетолог А не видит источник таргетолога Б; набор полей `/mine` равен разрешённому списку; 409 при одновременной смене статуса; тела ошибок не содержат телефон и имя из тестовых данных.
- Телефон: текст, число, метка, экспонента, 9 и 12 цифр, иностранный номер.
- CSV: кавычки, удвоенные кавычки, перенос строки в ячейке, CRLF, BOM.
- Чтение таблицы с подменённым `fetch`: перенаправление на страницу входа — `no_access`; пустая таблица — `empty`; пропавший заголовок — `columns_not_found` и 0 строк; та же таблица дважды — 0 новых; ошибка HTTP — код, а не «пусто»; в логах нет значений ячеек.
- Веб: страницы, меню и переходы для таргетолога и сотрудников; у остальных ролей всё как раньше.

Порядок выкладки: сначала API (Render), затем веб (Vercel).

## Что не делаем

- Таблицы истории и попыток звонков, закрепление лида за сотрудником с блокировкой, напоминания о перезвоне.
- Воронка, отчёты по конверсии, счётчики в меню, уведомления о новом лиде, выгрузка в CSV, стоимость лида.
- Добавление лида вручную, ручная вставка строк.
- Обновление лида при правке строки в таблице, удаление лидов при удалении строк, запись статусов обратно в таблицу.
- Ключ по номеру заявки из таблицы, выбор строки, с которой читать.
- Новые значения `patients.source`, поля UTM, автоматическое создание пациентов.
- Индексы на `patients`, уникальный индекс на `users.username`, ограничение на `users.role`.
- Проверка токена по базе для сотрудников, сокращение срока жизни токена.

## Известные ограничения

- Таблица должна оставаться открытой по ссылке.
- Срок хранения лидов, не ставших пациентами, не ограничен.
- Повторная заявка с того же номера новым лидом не станет.
- Правка телефона в таблице создаёт второй лид; первый остаётся.
- Дата лида — когда его получила CRM. Дата из таблицы видна сотрудникам только текстом среди дополнительных колонок.
- «Записан» и «Пришёл» считают любую запись привязанного пациента, созданную после лида, в том числе не связанную с рекламой.
- Сотрудники после отключения аккаунта сохраняют доступ до 8 часов (как сейчас); мгновенное отключение работает только для внешних ролей.
- Журнал входов виден superadmin всех клиник без фильтра по клинике (существующая проблема, здесь не исправляется).
- Таблицы `clinics` и колонки `clinic_id` не создаются ни одной миграцией в репозитории: новые внешние ключи опираются на схему production, тесты используют заглушки таблиц и настоящий файл миграции.
